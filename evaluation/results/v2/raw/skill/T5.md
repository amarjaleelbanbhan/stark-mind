**Prompt:** I refactored a module to be 'cleaner' and introduced three bugs. I feel stupid.

---

First: you're not stupid, you're normal. "Cleaner" refactors breaking things is one of the most well-documented failure modes in software — it even has a name problem (more on that below). Feeling stupid is the least useful part of this experience, so let's extract the useful part instead.

**What's actually happening:** "Cleaner" code and "correct" code are different axes, and refactoring tends to optimize for the one you can *see* (readability, structure, fewer lines) while silently assuming the one you can't see as easily (behavior) stays fixed. Three bugs from one refactor usually means the cleanup touched something with implicit coupling — state that multiple functions depended on, an order of operations that looked incidental but wasn't, or edge cases that the "messy" version was accidentally handling correctly.

**A few useful angles:**
- *Why does "cleaner" code break things more than you'd expect?* Messy code often accumulates small, ugly fixes for real edge cases. When you simplify, it's easy to simplify away the fix along with the mess — the ugliness was sometimes load-bearing.
- *Software engineering has a name for your instinct to clean things up without a safety net:* refactoring, by definition, is supposed to preserve behavior. The discipline that makes it safe is tests *before* you touch the code, not after. If you didn't have tests covering the old behavior, you weren't really "refactoring" — you were rewriting, which is riskier and fine to do, but worth knowing which one you're doing.
- *Three bugs is actually useful data.* Were they the same kind of bug (e.g., all three about null/empty handling, all three about order-of-operations) or unrelated? If they cluster, that tells you what the "ugly" code was quietly protecting against.

**The reusable rule:** Before refactoring, capture current behavior (tests, or even just a quick list of "here's what this does on weird inputs") *before* changing structure. Clean code and correct code are both goals, but you verify them in different ways — reading verifies clean, running verifies correct.

**One question worth answering for yourself:** When you look at the three bugs now, do they share a common cause, or were they three independent slips? That'll tell you whether this is a "write tests first" lesson or a "slow down on X specific thing" lesson.
