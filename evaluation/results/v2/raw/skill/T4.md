**Prompt:** Why does adding an index to a database sometimes make queries slower?

---

**What might be happening?**

An index isn't free — it's a separate data structure the database has to maintain and *choose to use*. Two different failure modes cause the slowdown:

1. **Write-side cost.** Every insert, update, or delete now has to update the index too, not just the table. If you're measuring a write-heavy workload, "adding an index" can slow down writes significantly even while it speeds up the specific read query you had in mind.

2. **Read-side cost — the more surprising one.** Databases use a query planner that estimates whether using an index will be cheaper than scanning the whole table. If a query will return a large fraction of the rows (say, more than ~10-20%), jumping between the index and the actual table rows (called a "bookmark lookup" or "random I/O") can be *more* expensive than just reading the table sequentially. Sequential reads are cheap; random reads scattered across disk (or even across memory pages) are not. So the planner correctly chooses a full scan — but if it misjudges (stale statistics, skewed data distribution, a parameter value that behaves very differently from the "typical" one it estimated for), it can pick the index path when it shouldn't, and the query gets slower.

**The deeper pattern**

This is a classic trade-off/estimation problem: the database is making a bet based on statistics about *how much data* and *how it's distributed*. An index is a shortcut that's only faster if you're looking for a small, specific subset. Add enough indexes and the maintenance cost (writes) and the planner's chance of misjudging (reads) both grow. It's similar to adding a cache or a specialized lookup table in software — great for the narrow case it was designed for, actively harmful if applied broadly or if the underlying data shape changes.

One concrete, common trigger: **stale statistics after a bulk data change**. The planner's estimate of row distribution is out of date, so it picks an index-based plan that was right yesterday but wrong today.

A small way to observe this yourself: run `EXPLAIN` (or `EXPLAIN ANALYZE`) on the query before and after adding the index, and look at whether it's doing an index scan returning a large number of rows versus a small one — that ratio is usually the tell.

Does this come from something you're actively seeing, or more of a "someone told me this happens, how" question? That changes whether it's worth digging into your specific planner's behavior.
