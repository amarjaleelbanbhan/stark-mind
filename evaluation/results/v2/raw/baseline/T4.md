# Why Indexes Can Make Queries Slower

This is a well-known counterintuitive issue in database performance. Here are the main reasons:

## 1. **Query Planner Chooses a Bad Plan**
The optimizer uses statistics to estimate costs, and sometimes it mistakenly *prefers* the index when a full table scan would actually be faster.
- **Low selectivity**: If an indexed column has few distinct values (e.g., a boolean `is_active` flag), the index might match 40% of rows. Using the index means jumping back and forth between the index and table (random I/O) for a huge chunk of the table — slower than just scanning sequentially.
- **Stale/inaccurate statistics**: If table stats haven't been updated after bulk inserts/deletes, the planner may misjudge how many rows match and pick the index when it shouldn't.

## 2. **Random I/O vs. Sequential I/O**
- A table scan reads data sequentially (fast, especially on spinning disks).
- An index lookup followed by a "bookmark lookup"/heap fetch (common in non-clustered/secondary indexes) jumps all over the table to fetch actual row data — lots of random disk access.
- If a query returns a large percentage of rows via an index, this random-access penalty can outweigh the benefit of narrowing down rows.

## 3. **Write Amplification (Indirect Slowdown)**
This doesn't slow the *read* query, but it slows the system overall:
- Every `INSERT`, `UPDATE`, or `DELETE` must also update every index on that table.
- More indexes = more B-tree maintenance, more page splits, more locking/contention — which can slow down the writes that often precede or run concurrently with your reads.

## 4. **Index Maintenance Overhead at Scale**
- Fragmented indexes (from frequent updates) can become inefficient, requiring more page reads than a fresh index would.
- Wide indexes or indexes on frequently-updated columns can bloat and degrade over time without maintenance (rebuild/reorganize).

## 5. **Covering Index Illusion**
If an index *doesn't* include all columns needed by the query, the database still has to do an extra lookup to the main table (heap/clustered index) for each row — adding overhead that sometimes exceeds just scanning the table directly.

## 6. **Too Many Indexes Confuse the Optimizer**
With many overlapping or redundant indexes, the planner has more options to evaluate and can occasionally pick a suboptimal one, especially in complex queries with joins.

## 7. **Small Tables**
For small tables, a full scan fits easily in memory/cache and is essentially instant — using an index adds overhead (extra B-tree traversal) with no real benefit.

---

### Rule of Thumb
Indexes are a trade-off: they speed up **selective** reads (small % of rows) at the cost of **write performance** and **storage**. They can hurt when:
- The query returns a large fraction of the table,
- Statistics are outdated,
- The index isn't selective enough,
- Or there are too many redundant indexes bloating write overhead.
